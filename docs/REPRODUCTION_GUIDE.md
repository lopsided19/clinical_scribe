# 现场复现与答辩操作说明

对应规则 PDF 文件第 4、9—10、11—21 页。以下是已实现程序的操作说明，具体系统、预算及时间限制仍以赛方赛前附件为准。

## 干净环境运行

1. 解压指定版本 `队伍编号_algorithm.zip`，确认 `main.py` 直接在解压根目录。
2. 使用 Python 3.11，执行 `python -m pip install -r requires.txt`。当前正式算法只用标准库；可加 `--no-index` 在离线环境验证安装。
3. 由赛方在根目录放置真实 `.env` 与 `input.json`。`.env` 仅含 MODEL_NAME 和完整 ENDPOINT，无密钥。不要使用开发 MOCK 配置参加正式评测。
4. 执行 `python main.py`，记录本次退出码。0 表示整批完成，允许单例失败；1/2 是任务级错误。不要把遗留旧输出误当新结果。
5. 检查 `run_log.json` 的 completed、输入输出哈希、病例数、调用次数、逐例状态和时间戳，并保留本次源码、配置、提示词、输入输出原件。
6. 不人工改写正式正文。用开发工具打包时，指定原始冻结目录：`python tools/build_submission.py --team-id REAL_TEAM_ID --run-dir FROZEN_RUN_DIR`。

工具会验证输入输出文件哈希、逐例输入输出哈希、调用总数、配置与提示词及源码对应关系；失败记录也保留。核验是文件一致性检查，不是日志签名或模型身份认证。

## 可现场回答的设计问题

- **一次调用如何产生三段正文？** 同一次请求返回五字段 JSON；原始 sources 完整保留，辅助台账提供来源位置、值与单位、状态及时间索引。
- **怎样避免编造正常结果？** 提示词约束并进行缺失/否定/时间规则检查；默认只写警告，不自动改写医学正文。规则并不能证明所有事实正确。
- **如何处理失败？** 保留原 case_id 与位置，写 failed/error，再处理下一例；整批原子写入输出。
- **如何保证调用合规？** 只读赛方地址，所有 HTTP 尝试共用每例预算，默认无重试；最终限值按技术附件统一配置。
- **创新是否证明有效？** 已有结构化事实、时间状态和来源检查的工程实现及受控测试；真实医学收益须通过同批病例、固定版本的真实模型对照说明，当前没有该证据。
- **是否严格确定？** 配置、提示词和随机种子固定记录；是否发送 seed 取决于接口支持。温度为零不能保证远程逐字确定，服务版本和随机性需核查。
- **公开数据有什么局限？** CMB 是教学描述，可能存在预训练污染与时序边界问题；MIMIC Demo 缺完整病史，适合结构和数值测试，均不等于赛方正式病例。
- **能否在新增资料后重新生成？** main.py 会处理当前输入，不缓存旧答案。截止点和新增资料的正式协议尚未发布，不能假设可以把截止点之后的资料混入当前首程。

## 真实效果评价准备

先完成 baseline、grounded 两个冻结运行，再执行：

```powershell
python tools/compare_runs.py --baseline BASELINE_DIR --candidate GROUNDED_DIR --report artifacts/comparison.json
python tools/prepare_clinical_review.py --baseline BASELINE_DIR --candidate GROUNDED_DIR --out-dir artifacts/clinical_review_round1
```

只把新目录中的 `reviewer/` 交给医学评审，`coordinator_only/` 留给协调人。每位评审保存独立的表，五维度逐项填写来源与生成句，失败结果也复核；未阅项保持未复核。两位评审完成后再对照方法映射、讨论争议与严重错误。工具不设置未经赛方确认的分值/权重，不自动计算临床总分。A/B 分配隐藏方法元数据，正文风格仍可能暴露方法，不能据此宣称完整严格盲法。

目前没有真实模型结果，工具会拒绝用标为 MOCK 的回显制作真实效果对照材料。自动测试中的人工夹具仅验证程序，不作为医学评审证据。
